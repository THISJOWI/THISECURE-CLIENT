# Environment Profiles: Multi-Server Switching + LDAP Per-Domain Lock

## Problem

Users cannot switch between Cloud and Self-Hosted environments after onboarding. The deployment mode is locked at registration. Changing the server URL requires manually editing SharedPreferences. There is no multi-environment support (e.g., Cloud + multiple self-hosted servers).

LDAP configuration has no "once per domain" enforcement. Any user can attempt LDAP configuration for a domain, and there's no two-step authorization (thisuite admin + TI domain admin).

## Design

### 1. EnvironmentProfile Model

```dart
class EnvironmentProfile {
  final String id;                    // UUID v4
  final String name;                  // User-given name: "Cloud", "Oficina", etc.
  final EnvironmentType type;         // cloud | selfHosted
  final String serverUrl;             // "https://api.thisjowi.com" | "http://192.168.1.100:8080"
  final DateTime createdAt;
  DateTime lastUsedAt;
}
```

**EnvironmentType** enum: `cloud`, `selfHosted`.

### 2. EnvironmentProfileManager (Singleton)

Manages all profiles with persistent storage:

```
EnvironmentProfileManager
├─ List<EnvironmentProfile> profiles
├─ EnvironmentProfile? activeProfile
│
├─ loadProfiles()          // Load from SharedPreferences
├─ saveProfile(p)          // Add/update profile
├─ deleteProfile(id)       // Remove profile (cannot delete active)
├─ switchTo(id)            // Set active, clear current session
│
├─ storageKeysFor(id)      // Returns prefixed keys for storage isolation
└─ activeProfileId         // Persisted in SharedPreferences
```

**Storage isolation per profile**: Each profile uses prefixed keys in SharedPreferences and flutter_secure_storage:

| Key | Type | Example |
|-----|------|---------|
| `profile_{id}_name` | String | "Cloud" |
| `profile_{id}_type` | String | "cloud" |
| `profile_{id}_url` | String | "https://api.thisjowi.com" |
| `profile_{id}_created_at` | String | ISO 8601 |
| `profile_{id}_last_used` | String | ISO 8601 |
| `profile_{id}_token` | Secure | JWT |
| `profile_{id}_refresh_token` | Secure | Refresh token |
| `profile_{id}_deployment_mode` | String | "Cloud" / "SelfHosted" |

### 3. Switching Flow

```
User taps "Switch Environment" in Settings
    ↓
Show current profiles list + "Add Environment" button
    ↓
User selects target profile (or creates new)
    ↓
Switch dialog:
    "Switching to [profile.name]. Your current session will end."
    [Cancel] [Switch & Logout]
    ↓
If user confirms:
    1. Save current login data to current profile storage
    2. Clear current session (token, etc.)
    3. Set new active profile ID
    4. Apply new server URL via ApiConfig.setManualBaseUrl()
    5. Navigate to Login screen
```

When adding a new Self-Hosted profile:
```
User taps "Add Environment" → selects type → enters server URL
    ↓
Test connection → GET {serverUrl}/health
    ↓
If OK → Save profile with type, URL, user-given name
    ↓
Switch to new profile → Navigate to Login/Register
```

### 4. Cloud Profile (Default)

A "Cloud" profile always exists by default. It is created on first app launch:
- id: `cloud`
- name: "Cloud"
- type: `cloud`
- serverUrl: null (uses .env default)
- createdAt: app install date

Cannot be deleted.

### 5. LDAP "Once Per Domain" Enforcement

This is enforced at the **core/auth backend** level, not the client.

**Client-side changes:**
- LDAP config screen stays only accessible to admin users in Self-Hosted profiles
- Before allowing LDAP config, the client calls `GET /v1/auth/ldap-status?domain={domain}`
- If `ldapConfigured: true`, the client shows "LDAP already configured for this domain" and blocks config

**Backend-side changes (core/auth):**
- `ldap_status` endpoint already exists at `GET /v1/auth/ldap-status`
- Enhance it: when an org already has `ldap_enabled = true`, return `ldapConfigured: true`
- New endpoint: `POST /v1/auth/ldap/authorize` — TI domain admin confirms the LDAP config
  - Receives: `{ domain, orgId, authCode }` (authCode generated by thisuite admin)
  - Only callable once per domain
  - On success: sets `ldap_enabled = true` on the organization, generates event `LDAP_CONFIG_AUTHORIZED`
- New endpoint: `POST /v1/auth/ldap/initiate` (thisuite admin)
  - Receives: `{ domain, ldapUrl, ldapBaseDn, ldapBindDn, ldapBindPassword, userSearchFilter, emailAttribute, fullNameAttribute }`
  - Validates domain not already LDAP-configured
  - Saves LDAP config to org (but `ldap_enabled` stays `false`)
  - Generates an `authCode`
  - Returns `{ authCode }` for the admin to communicate to TI admin

**Two-step flow:**
```
1. thisuite admin initiates (client → POST /v1/auth/ldap/initiate)
   ├─ Saves LDAP config to org, ldap_enabled = false
   └─ Returns authCode

2. TI domain admin authorizes (client → POST /v1/auth/ldap/authorize)
   ├─ Receives domain + authCode
   ├─ Sets ldap_enabled = true
   └─ Domain is now locked (no other org can configure LDAP for it)
```

**What prevents reconfiguration:** The `organizations` table's `domain` field and the `ldap_enabled` flag. Once `ldap_enabled = true` for an org with domain X, any attempt to configure LDAP for domain X on any org returns `409 Conflict`.

### 6. UI Changes

**Settings screen** — new "Environments" section:
```
Settings
├─ Profile (avatar, name, country)
├─ Security (password, biometric)
├─ Environments                          ← NEW
│   └─ Shows current profile name + type
│   └─ Tap → Environment Manager screen
├─ LDAP Configuration (only visible for SelfHosted admin)
├─ Import/Export
└─ Debug
```

**New screens:**
- `EnvironmentListScreen` — list of profiles with active indicator, add/switch/delete
- `EnvironmentAddScreen` — form to add new profile (name, type, server URL, test connection)

### 7. DeploymentProvider Deprecation

The existing `DeploymentProvider` becomes a thin wrapper over `EnvironmentProfileManager`:

```dart
class DeploymentProvider extends ChangeNotifier {
  bool get isSelfHosted =>
      EnvironmentProfileManager.instance.activeProfile?.type == EnvironmentType.selfHosted;
  bool get isCloud =>
      EnvironmentProfileManager.instance.activeProfile?.type == EnvironmentType.cloud;
  // ... other methods delegate to EnvironmentProfileManager
}
```

### 10. Non-Goals

- Data migration between environments (out of scope per user requirement)
- Simultaneous connections to multiple environments
- Deleting a profile while having active data in it (user must log in first to delete)
- Cloud LDAP (LDAP only makes sense in Self-Hosted mode)
